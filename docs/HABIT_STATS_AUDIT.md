### Issue detail

**1. [high] habit_stats.current_streak** — group `streak`, parity `DIVERGE`  
- *Correct implementation:* Mobile Dart / Desktop Dart (computeStreak persisted to goal_logs.streak) produce the mathematically correct streak. The cloud SQL habit_stats view formula is only a passive read of that persisted value; its output is correct ONLY when the latest log row was written by a client that ran computeStreak. The web toggleLogMutation is the defective write path — it fails to persist streak, making the shared cloud view report stale/zero streaks for any goal whose most-recent log was toggled from the web.  
- *Discrepancy:* The web client (src/hooks/useGoals.ts:267-274 toggleLogMutation) upserts goal_logs with only {goal_id,date,status,user_id} and NEVER writes the streak column — the column is not even present in src/integrations/supabase/types.ts goal_logs Row/Insert (lines 108-129). So for any habit toggled from the web, the persisted streak stays at the DB default (0) or a stale prior value. Concrete input: brand-new habit, user marks TODAY 'done' via the web app → goal_logs row has streak=0 (default) → habit_stats.current_streak = 0. The exact same action from mobile-Dart or desktop-Dart writes streak=1 (computeStreak) → current_streak = 1. The three sources are NOT equivalent: web-written cloud rows make the view report 0 where Dart-written rows report the true streak.  
- *Fix status:* OPEN — web client fails to persist the streak column (group C).

**2. [high] habit_stats.worst_streak** — group `streak`, parity `DIVERGE`  
- *Correct implementation:* mobile-Dart and desktop-Dart. Their write paths persist the correct signed streak via computeStreak (negative for 'missed'), and their read formula matches the SQL view. The cloud SQL view formula is itself correct but is fed unpopulated (NULL/0) streaks by the web client, which never writes the streak column — making cloud-mode worst_streak wrong (0) for web-logged habits.  
- *Discrepancy:* Same two defects as best_streak, mirrored for negative runs. (1) Web: no streak persisted → worst_streak always 0. Concrete: mark 3 consecutive days 'missed' on the web → all rows streak=0 → worst_streak=0 (should be 3); mobile/desktop write -1,-2,-3 → worst_streak=3. (2) Dart mid-history edit staleness: fill an unlogged gap between two missed runs by toggling the gap day to 'missed' — only that day's streak is recomputed, later missed rows keep stale shallower negatives, so abs(min(...)) understates the true longest missed streak. mobile-Dart and desktop-Dart MATCH each other; both diverge from the true computeStreak value the SQL view is supposed to reflect.  
- *Fix status:* OPEN — web client fails to persist the streak column (group C).

**3. [high] computeBestHabits / get_best_habits** — group `global_rankings`, parity `DIVERGE`  
- *Correct implementation:* SQL get_best_habits and both Dart computeBestHabits mirrors are correct GIVEN a canonical token. The mobile cloud caller (goal_provider.dart:894) and desktop private caller (statistics_rpc_providers.dart:82) supply canonical tokens correctly. The bug is solely in the desktop CLOUD caller (statistics_rpc_providers.dart:88-90), which passes the raw UI token.  
- *Discrepancy:* The desktop CLOUD caller sends a NON-canonical timeframe token to the SQL RPC, so get_best_habits returns all-zero rates. desktop/lib/features/statistics/data/statistics_rpc_providers.dart:82 canonicalises for the private path but line 88-90 calls `_listRpc('get_best_habits', extraParams:{'p_timeframe': timeframe})` with the RAW UI token. The desktop UI (statistics_page.dart:508 / :36-39) only ever passes 'timeframe_week_short' | 'timeframe_month_short' | 'timeframe_year_short' | 'timeframe_all'. SQL get_best_habits matches only 'week'/'month'/'year'/'all', so EVERY desktop-cloud call hits no window branch -> filtered_logs empty -> every goal rate=0.0, list ordered by streak only. Mobile (goal_provider.dart:894) canonicalises ONCE and passes the canonical token to BOTH private and cloud RPC, so mobile cloud is correct. Concrete: Cloud mode, goal A rate 90%/last-7d streak 0, goal B rate 20% streak 10, 'Week' tab. Mobile cloud + both private impls -> A ranked above B by rate. Desktop cloud -> both rate 0.0, B ranked above A by streak. Fix: pass canonicalBestHabitsTimeframe(timeframe) at statistics_rpc_providers.dart:89. (Secondary, low: DST in Dart age<=windowDays via inDays can misbucket a boundary log vs SQL DATE math, same mechanism as critical_habits.)  
- *Fix status:* FIXED (desktop) — cloud caller now canonicalises the timeframe token.

**4. [high] computeGlobalTrend YEAR (timeframe_year_short) — 24 monthly averages** — group `global_trend`, parity `DIVERGE`  
- *Correct implementation:* Dart (mobile and desktop, which are identical); the SQL timeframe_year_short branch is buggy because day_stats reads FROM active_goals instead of FROM day_range LEFT JOIN active_goals, dropping empty days and empty months.  
- *Discrepancy:* today=2026-07-14, one goal start_date=2026-07-10, end_date=NULL, frequency=every day. Logs: 2026-07-10='done', 07-11..07-14 no log. YEAR: Dart emits 24 points — 23 prior months at rate 100 (all days empty) and July2026 (point_index 23) = mean over July 1-14 = (100×9 empty + 100 for the 10th + 0×4)/14 = 1000/14 ≈ 71.43. SQL emits ONLY 1 row (point_index 23), rate = mean over active days 10-14 = (100 + 0×4)/5 = 20.0. So 24 points vs 1 point, and the July value is 71.43 vs 20.0.  
- *Fix status:* OPEN — cloud SQL bug, needs a migration (group B).

**5. [high] computeGlobalTrend ALL (timeframe_all) — ~10 bucketed averages** — group `global_trend`, parity `DIVERGE`

The cloud SQL get_global_trend timeframe_all branch is the buggy one: its inner join on active_goals drops non-active days from the average, mislabels bucket dates with MIN(active date), and omits empty buckets, yielding e.g. 0.0 instead of 80.0.  
- *Discrepancy:* today=2026-07-14, one goal start_date=2026-06-01, frequency=[1] (Mondays only), status 'missed' on every Monday, no other logs. ALL: earliest=2026-06-01, days=43, interval=ceil(43/10)=5, pointsCount=10, 5-day buckets. Dart bucket 0 = [06-01..06-05]: one Monday (06-01, missed→0) + four non-Mondays (empty→100) → mean=(0+100×4)/5=80.0, label 2026-06-01. SQL bucket 0: only the active Monday 06-01 counts → mean=0.0, label 2026-06-01. Later buckets whose start is a non-Monday also get different date labels (Dart=bucket start, SQL=first Monday inside). Value 80.0 vs 0.0 and shifted labels.  
- *Fix status:* OPEN — cloud SQL bug, needs a migration (group B).

**7. [medium] computeStreak (signed streak function — foundation of current/best/worst)** — group `streak`, parity `MATCH`

**10. [medium] _performanceComparisonCards (best-vs-worst streak gap) vs mobile _calculateConfrontoData** — group `desktop_perhabit_extra`, parity `DIVERGE`

**11. [low] total_active_days** — group `habit_stats`, parity `DIVERGE`  
- *Correct implementation:* SQL (the habit_stats view). Postgres date subtraction is pure calendar arithmetic and is immune to DST; both Dart clients share the identical Duration.inDays truncation bug on local-midnight DateTimes and undercount by 1 across a spring-forward transition.  
- *Discrepancy:* Local zone America/New_York, start_date=2026-03-07, today=2026-03-09 (spring-forward was 2026-03-08). Calendar span inclusive = 3 days. SQL: 2026-03-09 − 2026-03-07 + 1 = 3. **12. [low] computeYearlyGrid (365 status codes)** — group `grid_perf`, parity `MATCH`  
- *Correct implementation:* SQL (get_habit_yearly_grid) — pure calendar-DATE arithmetic via generate_series/INTERVAL is DST-immune; both Dart clients share the latent Duration(days) date-walk bug.  
- *Discrepancy:* Algorithm is 3-way identical. Sole caveat is a Dart-runtime DST artifact in the date walk `start.add(Duration(days:i))` (desktop:137 / mobile:127): Duration adds absolute 24h, so a date iteration crossing a fall-back (25-hour) transition can land at 23:00 of the previous calendar day, duplicating one grid cell's date and skipping the next. Concrete input: timezone Australia/Sydney (fall-back first Sunday of April), today just after that transition so the 365-day window's first DST crossing is the fall-back; the grid cell for the transition day gets the prior day's status while the following day is dropped, whereas the SQL pure-DATE arithmetic is immune. Both Dart clients share the bug (mobile==desktop), and US/EU windows spanning a full year self-cancel (spring-forward pushes to 01:00, safe), so real-world impact is narrow — hence low, not a hard divergence.  
- *Fix status:* OPEN — shared Dart DST date-walk (group A).

**13. [low] computeCriticalHabits / get_critical_habits** — group `global_rankings`, parity `MATCH`

Dart computes age = DateTime(y,m,d).difference(date).inDays, which truncates real elapsed microseconds; SQL uses pure DATE subtraction. **14. [low] Habit co-completion percentage — single target (computeHabitCorrelations)** — group `correlations_mood`, parity `DIVERGE`

## Full per-stat reference

### Core per-habit stats (habit_stats view)

#### current_streak — ✅ MATCH  ·  🟡 low
*Implementations:* sql: habit_stats latest_logs CTE / current_streak; desktop: computeHabitStatsRow; mobile: computeHabitStatsRow  
*Formula:* Streak value of the goal_log with the maximum date. SQL: DISTINCT ON (goal_id) ... ORDER BY goal_id, date DESC → COALESCE(streak, 0) (migrations/20260622_add_habit_stats_view.sql:5-15). Dart: latest = log with max date via l.date.isAfter(latest.date); return latest?.streak ?? 0 (desktop private_analytics.dart:94,118; mobile:90,110). Status of the latest row is irrelevant in all three.  
*Edge cases:* Empty logs → 0 in all three (SQL COALESCE, Dart null-coalesce). Single log → its streak, all match. Ties on same date: SQL DISTINCT ON with no tie-break column picks a NONDETERMINISTIC row among same-date logs; Dart keeps the FIRST in input-list order (isAfter is strict, so a later equal-date log does not replace). Only reachable if a goal has 2+ logs on one calendar day (normally blocked by a per-goal-per-date uniqueness), so low real-world exposure.  
*Note:* Only diverges if a single goal has two logs with the same date but different streak values, e.g. goal G with (date=2026-07-14, streak=5) and (date=2026-07-14, streak=-1): Dart returns 5 (first in list), Postgres may return either depending on scan order. Not reachable under the normal one-log-per-day invariant.  

#### best_streak — ✅ MATCH
*Implementations:* sql: best_streak subquery; desktop/mobile: computeHabitStatsRow bestDone  
*Formula:* max(streak) over logs WHERE status='done', COALESCE to 0. SQL lines 16-18. Dart: bestDone = max of l.streak among status=='done', else 0 (desktop:95-97,119; mobile:91-93,111).  
*Edge cases:* No 'done' logs → SQL max()=NULL→0; Dart bestDone=null→0. MATCH. Single done → that streak. Negative done streak (data anomaly) → max still selects the largest; both identical. 'skipped' never contributes in either.  

#### worst_streak — ✅ MATCH
*Implementations:* sql: worst_streak subquery; desktop/mobile: computeHabitStatsRow worstMissed  
*Formula:* abs(min(streak)) over logs WHERE status='missed', COALESCE to 0. SQL lines 19-21. Dart: worstMissed = min of l.streak among status=='missed'; return worstMissed==null ? 0 : worstMissed.abs() (desktop:98-103,120; mobile:94-96,112).  
*Edge cases:* No 'missed' logs → SQL min()=NULL→0; Dart null→0. MATCH. If missed streaks are stored positive instead of negative, abs(min) == min in both, still identical. Single missed → abs of its streak in both.  

#### total_completions — ✅ MATCH
*Implementations:* sql: total_completions subquery; desktop/mobile: totalCompletions  
*Formula:* count(*) WHERE status='done', COALESCE 0 (SQL 22-24). Dart: increment totalCompletions per done log (desktop:92; mobile:92). Integer, no rounding.  
*Edge cases:* Empty → 0 both. 'skipped' excluded both. No division. Fully equivalent.  

#### missed_days — ✅ MATCH

*Formula:* Per goal, dates = sorted 'done' log dates; require ≥3 (⇒ ≥2 gaps). gaps[i]=dates[i].diff(dates[i-1]).inDays. mean=Σgaps/len. If mean<=0 → score 100. #### computeMomentumScore — 🖥️ DESKTOP-ONLY
*Implementations:* desktop: analytics_extra.dart:557-579  
*Formula:* streakHealth = (Σ over streaks of clamp(current/max(best,1),0,1))/n, 0 if n==0. r7=clamp(rate7,0,1). trend=clamp(0.5+(rate7−ratePrev7),0,1). score=(0.5*r7 + 0.3*streakHealth + 0.2*trend)*100. Weights 0.5/0.3/0.2 sum to 1.0.
