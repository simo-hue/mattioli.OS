## Tier 2 — App Review exposure

### A1. ~~A reinstall reaches Supabase before the consent screen~~ — **FIXED**

> Two review rounds, ten defects. The gate itself was right; everything around it was not. Worst: the consent screen read `isLoggedIn` BEFORE adopting the session, so `updateConsentInDb` — its only server-side write — silently stopped firing on exactly the reinstall path this fix exists for. Adopting before persisting the flag closed that, the `/choose` flash, and a race where tapping "continue without an account" mid-await got overwritten with an account-mode state. The background isolate was still carrying the old predicate. 1019 tests green.
>
> **Still needs your on-device pass** — the mechanism is a real Keychain surviving a real app deletion, which no simulator reproduces. Install, sign in, delete the app, reinstall, confirm the consent screen appears with no Supabase traffic before Continue.

`lib/main.dart:78` initialises Supabase gated **only** on private mode:

```dart
if (!startsInPrivateMode) {
  await Supabase.initialize(... localStorage: SecureLocalStorage());
  unawaited(NotificationService().replayPendingHabitLogs());
}
```

`SecureStorageUtils` stores the session with
`KeychainAccessibility.first_unlock` (`secure_storage_utils.dart:14`). iOS
Keychain items survive app deletion; `NSUserDefaults` does not. So on a
reinstall `has_completed_consent` is gone (the router correctly sends the user
to `/consent`) while the session is still there — and the SDK restores it,
refreshing the token over the network, before the user has answered anything.
`replayPendingHabitLogs()` can write on the same path.

Compare `SentryService.shouldRun(...)` at `main.dart:171`, which exists for
precisely this reason and gates on the question being **answered**, not on the
answer. Supabase has no equivalent.

**Fix shape:** an extracted `shouldInitialiseSupabase({hasCompletedConsent,
isPrivateMode})` predicate, unit-tested like `SentryService.shouldRun`, with
initialisation deferred to `ConsentScreen` on a fresh answer.

**Proof:** predicate-level unit test. A full simulator demo needs a signed-in
account, and I won't enter credentials — the code path and the Keychain
accessibility flag are unambiguous on their own.

### A2. ~~The paywall claims BYOK works~~ — **FIXED**

> Two strings in the audit; **five** in the code. Three review rounds, and the interesting part is that my first two *replacement* drafts were themselves false: draft 1 merely echoed the row title and told a non-subscriber to "manage" a subscription they do not hold; draft 2 replaced that with capability claims — "reads your own habit history" — that the coach cannot honour, since `_getSystemPrompt` sends the user's name and TODAY's completion count and nothing else. Shipped copy claims only what the code does. 1012 tests green.

### A9. ~~The AI Coach setup card's only button is a dead end~~ — **FIXED**

`ai_chat_screen.dart` shows this card when no transport resolves — in account mode, that means "not Pro". Its single action opens `AppSettingsScreen`, which contains **no navigation at all** (zero `Navigator.push`), and whose only subscription item opens Apple's external manage-subscriptions page. `SubscriptionScreen` is reachable from Profile, the habit sheet and the Pro modal — but not from where this button lands. A user told the coach comes with Pro is sent to a screen that cannot sell it. Redirecting the button is a behaviour change, so it is reported rather than done.

Two strings promise a free bring-your-own-key path:

- `translations_en.g.dart:1729` — *"…Prefer your own OpenRouter account? That's
  free too."* → `pro_features_modal.dart:165`
- `translations_en.g.dart:3702` — *"Your own OpenRouter account works too,
  free."* → `subscription_screen.dart:747`

`coach_endpoint.dart:117` is explicit: `if (isPrivate) return hasKey ?
CoachMode.byok : null;` — **account mode never resolves to BYOK.** Both strings
render on Pro-purchase surfaces, which are account-mode only. The claim is false
exactly where it is made, on the 3.1.2(c) surface.

**Fix shape:** copy-only, but it is a factually-false string so it clears the
Q3 bar. 35 locales.

## Tier 1 — data loss / corruption

### A3. ~~A check-in from a notification writes a `goal_logs` row with no `streak`~~ — **FIXED**

> Closed after five adversarial review rounds. The fix itself was right the first time; the rounds found four defects in HOW it was done — an unordered paged read that could write a truncated streak over a correct one, an unbounded read that could lose the tap in a reclaimed background isolate, a status-blind dequeue that erased a later verdict, and a `pending` report that could let auto-fail overwrite a tapped Done after midnight. 1004 tests green.

`notifications.dart:278` (account mode) upserts a bare payload:

```dart
await Supabase.instance.client.from('goal_logs').upsert({
  'user_id': user.id, 'goal_id': habitId, 'date': dateKey, 'status': status,
}, onConflict: 'goal_id, date');
```

The in-app path does **not** — `goal_provider.dart:1471` goes through
`goalLogUpsertPayload(..., streak: newStreak)`. On a new day the notification
path INSERTs, so `streak` lands NULL.

`schema.sql:124` says that column is *"read by the habit_stats view
(migrations/20260622_add_habit_stats_view.sql), which cannot be created without
it"*. And the repair that exists — `runStreakRepairOnce`, `main.dart:750` — is
**Private mode only** and runs once per install, so an account-mode row written
this way stays wrong forever.

Net effect: answering a reminder from the lock screen instead of opening the app
silently degrades that habit's statistics, permanently.

**Proof:** a test asserting both writers produce the same column set.

### A4. ~~Deleting a habit on iOS destroys its whole history~~ — **FIXED (smart delete, at your request)**

> Three review rounds. Beyond the feature itself they found: an archived habit's reminder being re-armed forever by the next settings change, with no screen left to cancel it; the history probe missing `goal_progress`, which cascades too (a quantitative habit can hold hundreds of progress rows and zero logs); and my own first empty-state fix blanking the whole calendar, hiding the very history the feature preserves. 1011 tests green.

`goal_provider.dart:851` — `await supabase.from('goals').delete().eq('id', id)`.
`schema.sql:119` — `goal_id uuid REFERENCES public.goals(id) ON DELETE CASCADE`.
So every log for that habit is gone.

The web app does not do this. `web-app/src/hooks/useGoals.ts:141` implements
`softDelete`, archiving a habit that still has logs by writing
`end_date = yesterday`, and hard-deletes only when the log count is zero.

Same user intent, two clients, opposite outcomes — and the iOS one is
irreversible. The confirmation dialog
(`habit_management_modal.dart:765`) says only *"Are you sure you want to
'X'?"*; it does not mention that the history goes with it.

**This one needs your decision, not a fix from me.** Matching the web app's
smart-delete would change what the delete button does, which is a feature change
under Q3. The cheap half — telling the user what they are about to lose — is
copy, and clears the bar.

## Tier 3 — functional wrongness a user can hit

### A5. ~~Life View shows a stranger's life when no date of birth is set~~ — **FIXED**

`life_view_widget.dart:15` — `int birthYear = 2003; // Fallback`. With no DOB
the screen renders a complete, plausible, wrong life: months lived, current age,
months remaining. Nothing signals that it is fabricated.

**Fix shape:** empty state prompting for a DOB. Clears the Q3 bar — the current
output is fabricated data.

### A6. ~~The reminder DST seed drifts by an hour~~ — **FIXED**

> Review corrected my own overclaim: the weekly loop can NOT produce a wrong weekday — it exits only when the weekday already matches. The real harm is the hour, which near midnight is a ~23-hour displacement within the correct day.

`notifications.dart:902` and `:912` step with `Duration(days: 1)` on a
`tz.TZDateTime`. A `Duration` day is a fixed 24 h, so a step across a
transition lands on a different wall-clock hour — the construction this repo's
own CI comment forbids for calendar arithmetic.

`matchDateTimeComponents` re-matches wall clock on every later firing, so only
the **seed** is affected, as your note says. But `_nextInstanceOfWeekdayTime`
(`:909`) loops the same step up to six times to reach the target weekday, so a
weekly reminder seeded across a transition can be off by an hour *and*, for a
time near midnight, land on the wrong weekday entirely.

**Fix shape:** build the next day by calendar
(`tz.TZDateTime(tz.local, y, m, d + 1, hour, minute)`). CI already runs
`TZ=Europe/Rome`, so a DST test will actually fire.

### A7. ~~Raw exception text is shown to users in three places~~ — **FIXED**

- `privacy_settings_screen.dart:849` — `'${...exportPrefix}$e'`
- `privacy_settings_screen.dart:1415` — `'${...resetPrefix}$e'`
- `privacy_settings_screen.dart:1521` — `'${...deletePrefix}$e'`

`main.dart` already states the rule — *"Raw exception text only in debug — don't
leak internals to users in release (SEC-7 / I18N-3)"* — and the global handler
honours it. These three don't. The interpolated text is also untranslated, on
the account-deletion path, in all 35 locales.

### A8. ~~A stale comment now documents the opposite of the code~~ — **FIXED**

`habit_management_modal.dart:785` still says ended habits are hidden because
*"the user can manage them from desktop"*. That is not true for an iOS-only
user, and it was the stated justification for a decision. In a repo where the
comment is the reasoning of record, this one actively misleads.

## Checked and clean

Worth recording so a later pass doesn't re-litigate them:

- **Cross-account cache leakage** — `cache_owner_user_id` guards both read and
  write sides; `cache_owner_guard_test.dart` pins both.
- **Account deletion teardown** — revokes Apple token before the RPC, clears
  goals/logs/macro goals/settings, drops the cache-owner marker, and purges the
  BYOK key in a `finally`. Thorough.
- **Biometric lock** — fails closed on error, opens only on genuine absence of
  enrolled biometrics, re-arms on `paused`.
- **Supabase pagination** — every read that can grow (`goal_logs`,
  `goal_progress`, export, import) uses `.range()`. The desktop defect
  (`TO_SIMO_DO` #1) has no mobile counterpart.
- **Hardcoded user-facing strings** — none found in `lib/ui/`.
- **`Duration(days:)` misuse** — only the two notification seeds above.
  `macro_goal_calendar.dart` looks similar but operates on `DateTime.utc`, which
  has no transitions, and is correct.
- **Notification writes** — correctly mode-gated; private mode never touches
  Supabase from the notification path.
- **Reorder index remapping** — the new `activePositions` mapping is correct,
  including ended-habit-in-the-middle cases. The `newIndex >= length` guard is
  not a drag-to-bottom bug: `onReorderItem` already subtracts one for the
  removed item.

## A10. ~~17 more exception leaks, in the statistics tabs~~ — **FIXED**

> Closed with an `EvolveAsyncError` kit widget that logs the error and shows the label. The guard in `no_raw_exception_in_user_copy_test.dart` now covers the `Text(...)` sink too, which it could not while these were live.

The same defect A7 fixed, in a shape A7's guard deliberately does not cover. Every
Riverpod async-error builder across the statistics widgets renders:

```dart
error: (err, stack) => Text('${context.t.common.status.error}: $err', ...)
```

`info_tab_widget.dart` (4), `global_trend_tab_widget.dart` (3),
`habit_overview_tab_widget.dart` (3), `global_alerts_tab_widget.dart` (2), and one
each in `habit_miglioramento`, `habit_calendario`, `habit_performance`,
`global_habits`, and `macro_goals_stats_view`. A PostgREST body — table names,
constraint names — rendered untranslated into the UI, in all five locales.

**Not swept into A7 because the fix is not the same.** The three toasts already
logged their exception via `AppLogger.error`, so dropping it from the message lost
nothing. These do not, and there is no `ProviderObserver` logging provider errors
either — so deleting the interpolation would lose the error entirely. Fixing them
properly means adding logging at 17 sites, which is a change worth deciding on
rather than slipping into a batch.
